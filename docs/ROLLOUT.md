# الإطلاق والترحيل والرجوع

## قبل أي بيانات إنتاج

توفر الجمعية: خادم/قاعدة/أرشيف/نسخ داخل المملكة، DNS وشهادة، مفاتيح تشفير وخزنة منفصلة، صلاحيات مجلس معتمدة، قائمة لجنة الاستبقاء ومرجع الجداول، مصدر Snso ووثيقة API وتصدير كامل، حساب الهوية/التوقيع والبريد/SMS. لا تستبدل `alehsan.org.sa` الحالي قبل توفير تشغيل Django فعلي وتحديد المسار/النطاق. المعاينة المنشورة ثابتة لا تشغل الخلفية ولا تسجيل دخول تشغيلياً.

## إعداد التطبيق

1. بيئات dev/test/prod منفصلة؛ secret وDB ومفاتيح وHR مختلفون. تركيب production `.env.example` وتشفير PostgreSQL/volumes وتقييد ports؛ DB غير منشور للعامة.
2. تثبيت scanner مع freshclam وتحديث signature databases، OCR ara، مكتبات WeasyPrint وveraPDF للمستندات الموقعة.
3. تشغيل `migrate`, `collectstatic`, `check --deploy`; إعداد MFA وعدم تعطيله في الإنتاج. `encrypt_media --commit` فقط بعد backup مشفر للملفات القديمة؛ الافتراضي dry-run. لا تفقد DATA_ENCRYPTION_KEY.
4. seed_demo ممنوع في الإنتاج؛ إزالة بيانات demo من بيئة staging منفصلة قبل القبول. لا حذف سجلات الجمعية الفعلية لتجربة الكود.
5. تشغيل web/scheduler/proxy، التحقق من healthy/readiness وسلاسل التدقيق وتوقيت الرياض.

## الترحيل

- inventory: عدد كل نوع/سنة/حالة/سرية، أقدم وأحدث IDs، حجم/عدد المرفقات، SHA256 وآخر sequence.
- mapping إلى JSON import_mail مع original reference وlegacy_id، أسماء الأطراف→Party، موظف→employee_number، وحدات وتصنيف واستبقاء، authorized للأسرار. المرفقات paths نسبية تحت مجلد التصدير وSHA256، التواريخ timezone-aware.
- `python manage.py import_mail history.json --actor <executive-number>` يتحقق دون حفظ سجل أو ملفات. اعزل دفعة اختبار ثم طابق counts/references/access/attachments.
- `--commit` بعد مطابقة معتمدة. الحقول الأصلية محفوظة، التوقيع القديم legacy_unverified حتى يتحقق من المزود. لا تستبدل توقيع قديم بوصفه شهادة صحيحة.
- تشغيل متوازٍ بزمن متفق عليه، مصدر قيد واحد أثناء الفترة لمنع issued numbers مزدوجة؛ مقارنة نهاية كل يوم. لا dual-write من دون مصدر فريد ومعرف حدث ثابت.
- freeze المصدر، دفعة delta أخيرة، تثبيت sequence، توقيع محضر reconciliation، cutover. راجع الأرقام قبل إعادة فتح التسجيل.

## الرجوع

يحفظ الإصدار السابق وصورة DB/media مشفرة قبل cutover. عند إخفاق القبول يُعاد توجيه read-only للمصدر السابق، تُوقف الإصدارات والتنبيهات الخارجية، ويُصدر جرد كل سجلات أحدث من checkpoint قبل الاستعادة. لا تعاد نسخة قديمة فوق تسجيلات جديدة دون reconciliation، ولا تعاد الأرقام الصادرة إلى sequence. الاستعادة على قاعدة معزولة أولاً وموافقة مسؤول البيانات على آلية الدمج، ثم تغيير الاتجاه DNS/proxy.

## مراقبة واستعادة

backup.sh نسخة طوارئ AES256-GCM، pgBackRest config: full يومي/incr كل ساعة/WAL خمس دقائق؛ التثبيت على DB ومستودع سعودي وخزنة مفاتيح مطلوبان، لم يتم تشغيله على إنتاج. تحقق restore drill كل ربع سنة وp95<2s تحت الحمل، RPO1h/RTO4h بمحضر. معيار قبول لا ادعاء فعلي من ملف cron.

|---|---|---|---|
| توسيع Django/PostgreSQL الحالي | تقدير تخطيطي 10–16 أسبوع عمل فريق (تحليل، ربط، QA، تشغيل)، لا عرض سعر؛ تكلفة السحابة ومزودي التوقيع/الهوية حسب عروض محلية | يعيد استخدام الأدوار والمهام، ملكية كود، يتطلب تشغيل وأمن | موصى به لهذا المشروع بناء على أمر المستخدم واستثمار النظام الحالي |
